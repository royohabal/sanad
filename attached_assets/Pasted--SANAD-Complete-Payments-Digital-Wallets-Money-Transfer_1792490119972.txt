## 2. Flow A — Tip a worker

Integrate payment into the existing public worker QR tipping page.

Expected flow:
1. Customer scans a worker's QR code.
2. Customer sees the correct worker's profile and tipping page.
3. Customer chooses a preset tip amount or enters a permitted custom amount in KWD.
4. Customer reviews the worker and amount.
5. Customer taps "Pay Tip".
6. Customer is redirected to Stripe Checkout in test mode if properly configured, or the simulated KWD checkout if not.
7. Customer sees a success, failure, or cancellation screen.
8. Only after verified payment success, record the tip and update the worker's tip history and applicable wallet/settlement records.

Requirements:
- Keep tipping as simple and quick as possible; customers should not need a SANAD account just to tip.
- Preserve existing worker QR IDs, tip records, ratings, and messages.
- Do not create duplicate tips if the customer refreshes the page or repeats a callback.
- Apply server-side validation and rate limiting to public tipping endpoints.
- Do not mark unpaid or cancelled tips as paid.

Expected flow:
1. Parent signs in.
2. Parent selects the child whose wallet they want to fund.
3. Parent taps "Add Money".
4. Parent chooses or enters a top-up amount in KWD.
5. Parent reviews the amount and selected child.
6. Parent taps "Continue to Payment".
7. The payment checkout opens.
8. After verified Stripe test payment or successful simulated demo payment, the child's wallet is credited exactly once.
9. Parent sees a confirmation with the amount added and the child's updated balance.

Requirements:

- Validate the child relationship and amount on the server.
- Cancelled or failed payments must not credit the wallet.
- Record the top-up in the child's wallet activity and the parent's transaction history.
- Prevent duplicate credits after refreshes, repeated requests, or repeated payment callbacks.
- Keep the child's balance and history consistent with the database.

## 4. Flow C — Send money to another individual

Implement or improve the existing individual-to-individual transfer feature.

Expected flow:
1. Authenticated user opens "Send Money".
2. User selects a recipient using the existing supported recipient lookup method.
3. User enters the amount in KWD and an optional note.
4. User reviews the recipient and amount.
5. User taps "Confirm Send".
6. If the sender has enough funds in their existing SANAD demo wallet, the transfer is completed internally.
7. Both sender and recipient see the updated balances and transaction history.
8. Both users can view a transaction receipt or detail page.

Requirements:
- Transfers from an existing SANAD balance should be internal wallet transfers. Do not redirect the user to Stripe to pay again for funds already in their wallet.
- Check sender identity, recipient identity, balance, amount, and permissions on the server.
- Prevent sending to invalid recipients, negative amounts, unauthorized wallets, or oneself if self-transfers are not supported.
- Prevent negative balances, double spending, and duplicate transfers.
- Use atomic database operations or transactions where supported.
- Record a unique transfer ID and corresponding debit and credit entries.
- If funds are insufficient, do not move money. Display a clear message and offer "Add Money" only if an appropriate top-up flow exists.
- Do not change balances merely because the browser claims a transfer succeeded.

## 5. Flow D — Request money from another individual

Implement or improve the existing "Request Money" functionality.

Expected flow:
1. Authenticated user opens "Request Money".
2. User selects the person they want to request money from.
3. User enters the amount in KWD and an optional note.
4. User reviews and sends the request.
5. The recipient receives an in-app request or notification and can view its details.
6. Recipient can accept and pay, decline, or take no action while the request is pending.
7. If accepted and paid successfully, complete the internal transfer exactly once.
8. Both users can see the resulting transaction and updated balances.

Requirements:
- Creating or viewing a request must never move money.
- Store a unique request ID, requester, requested-from user, amount, optional note, creation time, and status.
- Use clear statuses such as Pending, Paid, Declined, and Cancelled.
- The recipient must explicitly approve the payment before funds are transferred.
- If the payer has insufficient funds, leave the request unpaid and explain the available options.
- Prevent a request from being paid twice, including through repeated button clicks, simultaneous requests, or page refreshes.
- Only authorized participants can view, accept, decline, or cancel a request.
- Validate all status changes on the server.
- Record completed transfers in both users' histories.
